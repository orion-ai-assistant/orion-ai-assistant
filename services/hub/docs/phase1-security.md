# Phase 1 security

Scope: Hub backend only. No UI, refresh tokens, tunnel, or Flutter edits.

## Changes and configuration

- All privileged admin operations require an explicitly configured, matching `ADMIN_API_KEY`; an absent/empty key never grants access. Comparisons use `hmac.compare_digest`. Settings schema is authenticated metadata accessible to ordinary users; `/health` remains public.
- Startup rejects an empty JWT secret everywhere and the development JWT secret in remote/production, Docker compose, or non-loopback CLI binds. Local development logs an explicit warning. Configure a strong random `JWT_SECRET_KEY` before exposed deployment. Both compose API services set `ORION_HUB_MODE=remote`; native `run_local.py` already binds loopback. The source `ORION_DEPLOYMENT_MODE` and `ORION_BIND_HOST` markers remain supported; any remote/prod deployment, bind, `ORION_HUB_MODE`, `ORION_INSTALL_MODE` or environment signal rejects the development secret. The Docker image retains remote deployment/bind defaults. The installer retains automatic 48-byte random secret generation when missing/default and preserves custom secrets; both replicas load local overrides. Programmatic servers/proxies must explicitly set a remote deployment marker because their bind host cannot be inferred from CLI arguments.
- Registration creates pending (`is_active=false`) accounts. Existing approved/active accounts are retained. The database default is migrated to false and inserts explicitly use false. The existing owner API is preserved: `PUT /api/v1/auth/users/{username}/approval`, `X-Admin-Key: <configured owner key>`, JSON `{"is_active":true}` (an empty JSON object `{}` retains the existing true default). `PATCH` on the same path accepts explicit `{"approved":true}` for the Phase 1 workflow. Both support false to deactivate; missing/wrong keys return 401, unknown users 404, database outage 503. Pending login retains the source API status 400 and approval-required detail. HTTP JWT and audio WebSocket handshakes check the stored account is active; a JWT with subject `global` cannot grant admin rights.
- Login retains the source Redis Lua policy: five attempts per exact account and ten per peer IP in a 60-second window; the next attempt returns 429 with `Retry-After: 60`. All attempts count, including successful ones. Redis failure rejects login with 503. The endpoint does not directly trust request forwarding headers. Trusted proxy configuration determines the ASGI peer address; shared NATs/proxies can share an IP limit. Username Unicode compatibility is retained; passwords longer than 72 UTF-8 bytes return 422 rather than bcrypt truncation/errors.
- Existing chat ownership checks protect state, history (including inline file attachments), rename/delete, and chat tools. Message submission to a foreign chat now returns 403/404 instead of an accepted failed job. SSE rejects foreign chat/user identifiers before subscribing and uses only the authenticated account channel. Explicit stop-turn IDs must match the accessible chat's active turn. Browser manager always hashes string account IDs, preventing a 64-character hex username from aliasing another account's profile directory; internal trusted Path restores remain supported.
- CORS retains the explicit `ORION_CORS_ORIGINS` allowlist plus loopback development origins and rejects `*` configuration. No credentialed wildcard is enabled.

## Existing client behavior and remaining risks

Hub dashboard stores `orion_token` in localStorage (`ui/js/api.js`). Flutter stores the token with FlutterSecureStorage under `orion_token:$hubUrl` (`main_app/app/lib/core/network/orion_api.dart`, inspected read-only); browser storage remains within the same-origin JavaScript/XSS trust boundary. No storage change was made. A later cookie/HttpOnly design needs coordinated CSRF, CORS, SSE and client work. [OWASP guidance](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html) explains JavaScript access to localStorage session data.

The existing dashboard registers then immediately attempts login; pending accounts receive an approval-required error detail and the auth modal stays open. Approval has an API workflow, not new UI. Query-string tokens/admin keys remain supported for current stream clients and can enter URL logs/history. Existing 24-hour access-token lifetime is unchanged. Existing active accounts and preexisting administrator keys (including predictable legacy installer defaults) remain; weak custom credentials require owner rotation. Active streams are checked at connection time; periodic stream revocation and device/session controls belong to Phase 3. Owner-approved users on this PC may use the existing shared desktop browser session; hashed per-account tool/config directories do not isolate the operating system browser's cookies. Pending registration is not throttled in this phase. Strong non-default secret quality is an operator responsibility.
