# Hub phase 1 security

New registrations are stored with `is_active=false`. The PC owner approves or disables an account with `PUT /api/v1/auth/users/{username}/approval`, `X-Admin-Key: <ADMIN_API_KEY>`, and JSON `{"is_active": true}` (or `false`). The response is `{"username": "...", "is_active": true}`. Missing/invalid administrator keys return 401; unknown accounts 404; database unavailability 503. Existing active accounts remain active. A pending account receives no login token, and disabled accounts cannot use an existing JWT or the audio WebSocket.

Set a unique, random `JWT_SECRET_KEY` before deployment. The installer generates a 48-byte random secret when missing or equal to the development default, preserves custom secrets, and writes local overrides used by both API replicas. Docker API images mark their binding as remote. Native `run_local.py` binds to loopback. `ORION_DEPLOYMENT_MODE=remote` or `production`, a non-loopback `ORION_BIND_HOST`, `UVICORN_HOST`, or Uvicorn CLI `--host` rejects the empty/default secret at lifespan startup before infrastructure starts. The local default emits a warning. Programmatic `uvicorn.run(..., host=...)` deployments must explicitly set deployment mode/bind environment because its Python arguments cannot be inferred by the application.

Login attempts use Redis atomic counters: five attempts per exact account and ten per transport IP in a 60-second window. Both successful and failed attempts count; the next attempt returns 429 and `Retry-After: 60`. Redis outages return 503. Forwarding headers cannot change the limiter address. A shared reverse proxy therefore shares the IP limit; tune deployment separately if needed. This limits attempts rather than locking an account indefinitely.

Administrator access requires a configured, non-empty matching key. Chat read/history/write/delete/rename/tool selection require the authenticated owner. Stop requests also validate that the requested turn belongs to the owned chat. SSE subscribes only to the authenticated user's channel; query IDs cannot select another channel. Attachments are embedded in chat message/history records; there is no independent file download/upload-by-ID endpoint in this Hub version. Their read isolation follows the chat history gate. `/health` remains public.

CORS permits explicit `ORION_CORS_ORIGINS` plus loopback development origins, rejects `*`, and does not allow credentials. CORS is a browser response policy, not authentication. Existing tests cover hostile origins and lookalike localhost domains.

Web token risk (left unchanged in this phase): the Hub dashboard persists `orion_token` in `localStorage`; JavaScript/XSS can read it, and it survives tab/browser closure. SSE and audio WebSocket put the bearer token in query strings because browser APIs cannot supply custom authorization headers; proxy logs/URL tooling can expose it. Flutter uses `flutter_secure_storage` with an origin-specific token key; its web implementation remains browser storage and exposed to same-origin script compromise. Prefer short-lived tokens and hardened browser storage/session design in the planned auth phase; HTTPS is necessary remotely. Existing active accounts and preexisting administrator keys (including installer legacy predictable defaults) are preserved; owners should rotate weak credentials before network exposure.

Validation: automatic phase 1 regression tests exercise foreign owner access and inline file history, forged SSE IDs, foreign turn stop, inactive registration/JWT/WebSocket, owner approval and DB outage, missing/wrong/Unicode administrator keys, Redis rate limits/outage, default-secret remote/binding/lifespan rejection, installer secret generation/preservation, API replica consistency, and public health. CORS hostile-origin tests and existing tests are run separately and as a full suite.

Final results: phase 1 security + CORS: 22 passed (19 new security tests, 3 existing CORS tests). Full Python suite: 227 passed, 10 skipped, 9 failed, with 38 subtests passed. Before this change the same isolated environment produced 208 passed, 10 skipped and the same 9 failures. These preexisting failures are seven `test_browser_manager` cases, one `test_browser_tools` case, and one `test_media_efficiency` case; no new failing test was introduced. Existing Node STT tests: 17 passed. The requirement that every phase 1 security regression passes is met; the full repository green-suite criterion is not met because of the nine baseline failures outside this phase.
